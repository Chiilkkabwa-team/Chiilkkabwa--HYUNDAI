# 3인 공동개발 가이드

기준: 2026-11-13 (dev 통합 브랜치 도입). 제품 요구사항은 **공식접수기획서 최종 DOCX**를 우선한다. 이 파일에는 팀원의 실명·이메일을 기록하지 않는다.

**필독 규정:** [COMPLIANCE_REGISTER.md](COMPLIANCE_REGISTER.md)(공식 규정 근거 대장)와 [SAFETY_RULES.md](SAFETY_RULES.md)(S01~S12 제품 안전·G1~G5 검증 게이트). 공식 공모전·Pleos 문서가 최상위이며, 구현 증거가 없는 규정 적합성은 `NOT_VERIFIED`로 표시한다.

## 1. Git 브랜치 정책 (우선 적용)

**기능 브랜치 → dev(통합·공동 검증) → main(최종 제출·안정 버전)**

| 브랜치 | 역할 | 누가 언제 병합하나? |
|---|---|---|
| `feature/*`, `fix/*`, `docs/*`, `chore/*` | 개발자 3명이 각각 최신 `dev`에서 분기해 독립 개발하는 브랜치 | 담당자는 작업 브랜치에만 커밋·푸시 |
| **`dev`** | 기능 간 통합·회귀 테스트·에뮬레이터 검증 | **통합 담당자**가 각 기능을 확인한 뒤 순차 병합. 개발자들은 `dev`에 직접 개발/푸시하지 않음 |
| **`main`** | 공모전 제출·발표·릴리스용 기준 버전 | **팀의 명시적 릴리스 승인** 후 통합 담당자가 `dev → main` 전용 PR로 병합. 평소에는 보존 |

**AI 안전장치:** Codex·Claude Code 등은 기능 개발 요청이나 테스트 통과를 `main` 병합 승인으로 해석하지 않는다. `main`으로 직접 commit/push, 강제 푸시, `feature → main` PR·merge, 자동 병합, 기본 브랜치 변경을 임의로 수행하지 않는다. `dev → main` 병합은 **'이번 릴리스 main 반영을 승인한다'는 명시적 사용자/팀 의사 결정**이 있어야 한다. 개발 중에는 `main`을 건드리지 말 것.

**개발 시작:** 새 클론의 기본 체크아웃이 `main`이어도, 반드시 최신 `dev`를 가져와 기능 브랜치를 만든다. `main`이 기본 브랜치라는 사실은 개발 기준이라는 뜻이 아니다.

**제출 버전 동결:** 공모전 제출 메일에 적은 `main` 커밋 SHA가 심사 기준이며, 이력·태그를 보존한다. 제출 이후 `dev`의 고도화 작업을 자동으로 `main`에 반영하지 않는다. 릴리스 전 제출 일정·공식 규정·실행 APK를 다시 확인한다.

## 2. 기존 합의 유지


- **개발 기준 브랜치는 `dev`이고 제출 기준은 `main`이다.** **기능 하나 = 담당 개발자 한 명 = 독립 작업 브랜치 하나**를 원칙으로 한다. 담당 기능이 확정되기 전에는 임의로 개발 과제를 배정하거나 착수하지 않는다.
- **PR 및 동료 리뷰는 필수가 아니다.** PR을 사용하면 제목/설명을 한국어로 짧게 적는다.
- 원칙적으로 `main`·`dev`에 직접 기능 코드를 커밋하거나 강제 푸시하지 않는다. 통합 담당자가 테스트된 변경만 `dev`에 순차적으로 병합하며, 최종 승인된 때에만 `dev → main`으로 출시한다.
- **팀원별 고정 폴더 제한은 없다.** 담당 기능에 필요한 UI·Core·Data·테스트·문서를 해당 개발자가 함께 수정한다. 다만 다른 기능과 공유하는 파일·인터페이스 변경은 먼저 팀 채팅/Issue에서 조율한다.
- 변경 사항을 작게 유지해 병합 충돌과 디버깅 범위를 줄인다. CI가 실패하거나 실행되지 않으면 원인 및 대체 검증 결과를 기록한다.
- 차량 안전·권한·신호 출처 관련 변경은 회귀 테스트 없이는 병합하지 않는다.
- 모든 기능 담당자는 작업 시작·종료 시 S-ID별 규정 준수 여부와 공식 근거·확인 날짜를 작성한다. 규정 위반 FAIL은 병합하지 않는다. 미검증 기능은 실제 차량/주행 경로에 노출하지 않으며, Mock/Stub 전용은 출처와 차단 조건을 명시한 경우 통합 담당자가 제한적으로 병합할 수 있다.
- 모의 입력, 에뮬레이터 수신, 실차 수신, 문서 확인을 서로 혼동하지 않는다.

## 3. 기능 단위 개발 (담당 기능은 추후 결정)

**A/B/C의 차량·Core·UI 폴더별 고정 담당 체계는 사용하지 않는다.** 세 명 모두 기능 단위로 작업하며, 어떤 기능을 누가 맡을지는 팀이 별도로 결정한다. 아래는 역할 배정표가 아니라 개발 절차다.

| 구분 | 운영 기준 |
|---|---|
| 기능 담당자 | 기능마다 개발자 **1명** 지정. 사용자 흐름 1개를 설계부터 UI·로직·데이터 연동·테스트·문서까지 책임 |
| 수정 허용 범위 | 담당 기능 구현에 필요한 `ui/`, `core/`, `data/`, `app/src/test/` 등 **계층 제한 없음** |
| 다른 기능 | 자신에게 배정되지 않은 기능을 AI가 임의 구현·변경하거나 대규모 리팩터링하지 않음 |
| 공유 데이터 계약 | 여러 기능이 의존하는 이벤트·차량 신호·세션 상태 모델의 **필드, 단위, 출처, 시간 기준, 실패 처리**를 구현 전에 합의 |
| 통합 담당 | 세 명 중 **한 명이 겸임**. 기능 브랜치 → `dev` 순차 통합 및 공동 검증 담당. 최종 승인 시 `dev → main` 릴리스 담당. 네 번째 개발자 아님 |

**공유 인터페이스 예시:** `VehicleSignals`, `Signals`, 세션 상태, 이벤트 기록 데이터 모델, 저장소 API. 기존 구현과 최종 DOCX를 먼저 살피고, 아직 정해지지 않은 인터페이스를 개별 AI가 독자적으로 확정하지 않는다.

**충돌 주의 파일:** `ChiilViewModel.kt`, `MainActivity.kt`, `VehicleSignals.kt`, `Signals.kt`, `AndroidManifest.xml`, `app/build.gradle.kts`, `README.md`, `docs/01_PRD.md`.
공통 파일이나 다른 기능의 계약을 바꾸기 전에는 관련 담당자와 통합 담당자에게 **변경 이유·새 인터페이스·영향 범위·작업 순서**를 짧게 공유하고 합의한다. 서로 다른 브랜치에서 같은 공통 파일을 무작정 수정하지 않는다.

**기능 착수 절차**
1. 기능 이름, 인수 기준, 담당자, 브랜치명을 팀에서 정한다. **이 규정 체계 반영은 담당자를 배정한 것이 아니다.** 미정이면 구현 전에 결정한다.
2. 다른 기능과 주고받는 입력·출력·이벤트 계약을 확인한다. 의존 기능이 미완성이면 합의된 Mock/Stub로 독립 개발한다.
3. 각자 최신 **`dev`에서** 기능 브랜치를 만들어 요청받은 기능 범위만 구현·검증한다. A의 이벤트 데이터 형식을 B/C가 기다릴 필요 없이 합의된 Mock/Stub로 병렬 개발할 수 있다.
4. 테스트 결과와 변경된 공유 계약뿐 아니라 적용 S-ID별 `PASS/FAIL/NOT_VERIFIED/NOT_APPLICABLE`, 원문 URL·검증 증거·차단 조건을 기록하고 통합 담당자가 한 브랜치씩 합친다.

## 4. 각 PC에서 작업 시작

PowerShell (이미 clone을 완료한 팀원은 다시 clone할 필요 없음):

~~~powershell
git fetch origin --prune
git switch dev  # 최초 1회: git switch -c dev --track origin/dev
git pull --ff-only origin dev
git switch -c feature/my-task
~~~

수정 후:

~~~powershell
git status
git add -p
git commit -m "feat: 기능 요약"
git push -u origin feature/my-task
~~~

담당 브랜치의 CI 결과를 확인하고 실제 실행 결과를 docs/VERIFICATION_LOG.md 양식으로 남긴다. 각 PC가 이미 `main`에 있으면 미커밋 파일을 보존한 상태에서 `dev`로 이동한다. `git push origin main` 및 `git merge ...`로 `main`에 직접 병합하는 작업은 승인 없이 금지한다.

**통합 담당자용 흐름:** 기능 검증 → 기능 브랜치의 `dev` 대상 PR 또는 합의된 수동 병합 → `dev` CI/통합 테스트 → 필요 시 수정. 기능 PR과 동료 리뷰는 선택이지만 안전·규정 검증은 필수.

**최종 릴리스:** 별도 팀 승인 → `dev` 검증/제출 SHA 결정 → `dev`를 head, `main`을 base로 하는 릴리스 PR → diff/CI/APK/공모전 규정 최종 확인 → 통합 담당자 병합 → `main` 릴리스 커밋·제출용 SHA 기록. **AI가 이 단계를 자동 수행해서는 안 된다.**

## 5. 병합 규칙 (기능→dev는 리뷰/PR 선택, dev→main은 승인 필수)

- 다른 개발자가 맡은 **기능·공유 인터페이스**와 충돌하는 수정이 있는지 통합 담당자에게 알린다.
- 통합 담당자는 최신 **`dev`를 기준으로 한 기능 브랜치씩** 병합한다. 기능별 PR 대상(base)은 `dev`이다. `main`을 base로 선택한 기능 PR은 잘못된 대상으로 정정한다.
- 병합 전에 관련 테스트, Android mock/vehicle 컴파일, 출처 표시, 안전 잠금과 [SAFETY_RULES.md](SAFETY_RULES.md)의 G1~G5 게이트를 확인한다. 에뮬레이터 미시험을 PASS로 승격하지 않는다.
- `dev` 병합 직후 `dev`에서 테스트를 재실행하고 결과를 기록한다. 최종 릴리스 시에는 별도의 `dev → main` PR과 팀 승인 후 `main`에서 테스트한다.
- 실패 시 원인을 해결하거나 해당 통합을 되돌린다. `dev`·`main` 모두 강제 푸시로 이력을 덮지 않는다.
- 1차 제출은 **`main`의 제출 기준 커밋/태그를 고정**해 `dev`의 개발 중 변경과 구분한다. 공모전 공식 제출 SHA와 실제 APK·영상의 버전이 일치해야 한다.
- **기술적 제한:** 현재 GitHub 비공개 저장소에서 서버 측 branch protection/ruleset을 설정할 수 없는 플랜 제한이 확인됐다. 지금은 문서·AI 지침·CI가 사고를 줄이는 장치지만 **잘못된 푸시를 GitHub 서버가 강제로 차단하는 상태는 아니다**. 가능해지면 GitHub 보호 규칙에서 `main` PR 필수, 직접 푸시·force push 금지, 필수 CI를 설정한다.

## 6. 문서와 제품 규칙

- 최종 DOCX: 제품 요구사항(아직 구현되지 않은 계획을 포함).
- docs/IMPLEMENTATION_STATUS.md: 현재 구현 사실. 반드시 기준 SHA와 코드 경로 명시.
- docs/VERIFICATION_LOG.md: 실제 테스트 결과. 기기, SDK, 일시, 증거를 기록.
- docs/FACT_AUDIT.md: 기존 Markdown의 정정 및 미해결 목록.
- 차량 제어 API 금지, 미확인 SDK 시그니처 추측 금지, 신호 불명 시 안전 잠금 우선.
- 계정·연락처·키스토어·토큰·운전자의 민감한 정보는 Git에 넣지 않는다.
