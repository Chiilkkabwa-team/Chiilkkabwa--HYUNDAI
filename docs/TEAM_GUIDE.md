# 3인 공동개발 가이드

기준: 2026-11-13 (개별 담당자의 dev 자체 병합 허용). 제품 요구사항은 **공식접수기획서 최종 DOCX**를 우선한다. 이 파일에는 팀원의 실명·이메일을 기록하지 않는다.

**필독 규정:** [COMPLIANCE_REGISTER.md](COMPLIANCE_REGISTER.md)(공식 규정 근거 대장)와 [SAFETY_RULES.md](SAFETY_RULES.md)(S01~S12 제품 안전·G1~G5 검증 게이트). 공식 공모전·Pleos 문서가 최상위이며, 구현 증거가 없는 규정 적합성은 `NOT_VERIFIED`로 표시한다.

## 1. Git 브랜치 정책 (우선 적용)

**기능 브랜치 → dev(통합·공동 검증) → main(최종 제출·안정 버전)**

| 브랜치 | 역할 | 누가 언제 병합하나? |
|---|---|---|
| `feature/*`, `fix/*`, `docs/*`, `chore/*` | 개발자 3명이 각각 최신 `dev`에서 분기해 독립 개발하는 브랜치 | 담당자는 작업 브랜치에만 커밋·푸시 |
| **`dev`** | 기능 통합·회귀 테스트·에뮬레이터 검증 | **각 기능 담당자가 자기 브랜치를 자체 검증 후 직접 병합·푸시 가능. 다른 팀원 컨펌·PR·리뷰 불필요.** `dev`에 곧장 기능 코드를 작성하지 않고 기능 브랜치 경유 |
| **`main`** | 공모전 제출·발표·릴리스용 기준 버전 | **팀의 명시적 릴리스 승인** 후 통합 담당자가 `dev → main` 전용 PR로 병합. 평소에는 보존 |

**AI 자체 병합 권한:** 기능 담당자가 AI에게 맡긴 작업 범위에 한해 **기능 브랜치→`dev`는 추가 확인 요청 없이 스스로 병합 가능**하다. 단, 병합 전 테스트·안전·규정 자체 확인과 충돌 해결은 필수다.

**AI `main` 안전장치:** Codex·Claude Code 등은 기능 개발 요청이나 테스트 통과를 `main` 병합 승인으로 해석하지 않는다. `main`으로 직접 commit/push, 강제 푸시, `feature → main` PR·merge, 자동 병합, 기본 브랜치 변경을 임의로 수행하지 않는다. `dev → main` 병합은 **'이번 릴리스 main 반영을 승인한다'는 명시적 사용자/팀 의사 결정**이 있어야 한다. 개발 중에는 `main`을 건드리지 말 것.

**개발 시작:** 새 클론의 기본 체크아웃이 `main`이어도, 반드시 최신 `dev`를 가져와 기능 브랜치를 만든다. `main`이 기본 브랜치라는 사실은 개발 기준이라는 뜻이 아니다.

**제출 버전 동결:** 공모전 제출 메일에 적은 `main` 커밋 SHA가 심사 기준이며, 이력·태그를 보존한다. 제출 이후 `dev`의 고도화 작업을 자동으로 `main`에 반영하지 않는다. 릴리스 전 제출 일정·공식 규정·실행 APK를 다시 확인한다.

## 2. 기존 합의 유지


- **개발 기준 브랜치는 `dev`이고 제출 기준은 `main`이다.** **기능 하나 = 담당 개발자 한 명 = 독립 작업 브랜치 하나**를 원칙으로 한다. 담당 기능이 확정되기 전에는 임의로 개발 과제를 배정하거나 착수하지 않는다.
- **기능→`dev`에서는 PR·동료 리뷰·승인·컨펌 대기가 모두 선택**이다. 담당자가 자체 테스트·규정 검증 후 직접 병합하고, 변경 요약만 팀에 공유한다. PR을 쓰는 경우 한국어로 짧게 작성한다.
- **`main`·`dev`에서 직접 기능을 작성하거나 강제 푸시하지 않는다.** 각 담당자가 자기 기능 브랜치를 거쳐 `dev`로 병합·푸시할 수 있다. `main`은 별도 승인된 `dev → main` 릴리스만 허용한다.
- **팀원별 고정 폴더 제한은 없다.** 담당 기능의 UI·Core·Data·테스트·문서를 해당 개발자가 수정한다. 공통 파일/인터페이스 변경은 영향·호환성과 테스트를 스스로 확인하고 팀 채팅/Issue에 기록한다. **별도 사전 컨펌을 기다릴 필요는 없다.**
- 변경 사항을 작게 유지해 병합 충돌과 디버깅 범위를 줄인다. CI가 실패하거나 실행되지 않으면 원인 및 대체 검증 결과를 기록한다.
- 차량 안전·권한·신호 출처 관련 변경은 회귀 테스트 없이는 병합하지 않는다.
- 모든 기능 담당자는 S-ID별 규정 준수와 근거·확인 날짜를 기록한다. **규정·안전 FAIL, 미해결 충돌, 관련 테스트 실패 상태에서는 `dev` 병합 금지.** 실차·주행 경로 미검증 기능은 기본 차단하며, 출처·차단 조건이 명시된 Mock/Stub 전용 기능은 **담당자 자체 검증 후 `dev` 통합 가능**하다.
- 모의 입력, 에뮬레이터 수신, 실차 수신, 문서 확인을 서로 혼동하지 않는다.

## 3. 기능 단위 개발 (담당 기능은 추후 결정)

**A/B/C의 차량·Core·UI 폴더별 고정 담당 체계는 사용하지 않는다.** 세 명 모두 기능 단위로 작업하며, 어떤 기능을 누가 맡을지는 팀이 별도로 결정한다. 아래는 역할 배정표가 아니라 개발 절차다.

| 구분 | 운영 기준 |
|---|---|
| 기능 담당자 | 기능마다 개발자 **1명** 지정. 사용자 흐름 1개를 설계부터 UI·로직·데이터 연동·테스트·문서까지 책임 |
| 수정 허용 범위 | 담당 기능 구현에 필요한 `ui/`, `core/`, `data/`, `app/src/test/` 등 **계층 제한 없음** |
| 다른 기능 | 자신에게 배정되지 않은 기능을 AI가 임의 구현·변경하거나 대규모 리팩터링하지 않음 |
| 공유 데이터 계약 | 기존 필드·단위·출처·시간 기준을 지키고, 변경 시 기존 소비자 호환·테스트를 확인해 문서화·팀에 공유. **동료 승인 대기는 없음** |
| `dev` 병합 담당 | **각 기능 개발자 본인**. 다른 사람의 승인·리뷰 없이 자체 병합하고 CI 사후 문제까지 책임 |
| `main` 릴리스 담당 | 세 명 중 팀이 정한 한 명이 겸임. **팀의 명시적 릴리스 승인** 후 `dev → main` 전용 PR로만 반영 |

**공유 인터페이스 예시:** `VehicleSignals`, `Signals`, 세션 상태, 이벤트 기록 데이터 모델, 저장소 API. 기존 계약을 우선하고, 새 계약은 최소 명세·Mock 예시를 먼저 공유한다. 각자는 **기존 기능이 깨지지 않도록 호환성 검증**을 책임지며, 동료 답변을 기다리는 것을 필수 절차로 두지 않는다.

**충돌 주의 파일:** `ChiilViewModel.kt`, `MainActivity.kt`, `VehicleSignals.kt`, `Signals.kt`, `AndroidManifest.xml`, `app/build.gradle.kts`, `README.md`, `docs/01_PRD.md`.
공통 파일/계약을 바꾸는 경우 **변경 이유·새 인터페이스·영향 범위**를 문서/팀 채팅에 기록하고, 최신 `dev`에서 충돌·소비자 호환성을 직접 검증한다. **다른 사람의 컨펌이 없어도 개발·병합할 수 있지만**, 기존 동작이 깨지거나 충돌 해결이 불가능하면 병합하지 않는다.

**기능 착수 절차**
1. 기능 이름, 인수 기준, 담당자, 브랜치명을 팀에서 정한다. **이 규정 체계 반영은 담당자를 배정한 것이 아니다.** 미정이면 구현 전에 결정한다.
2. 다른 기능과 주고받는 입력·출력·이벤트 계약을 확인한다. 의존 기능이 미완성이면 합의된 Mock/Stub로 독립 개발한다.
3. 각자 최신 **`dev`에서** 기능 브랜치를 만들어 요청받은 기능 범위만 구현·검증한다. A의 이벤트 데이터 형식을 B/C가 기다릴 필요 없이 합의된 Mock/Stub로 병렬 개발할 수 있다.
4. 담당자가 관련 테스트·규정 게이트를 자체 확인하고 변경사항·검증 증거를 기록한 뒤 **본인 브랜치를 `dev`에 직접 병합**한다. 다른 팀원의 검토·승인은 요구하지 않는다. 충돌 또는 실패가 발생하면 담당자가 해결한다.

## 4. 각 PC에서 작업 시작

PowerShell (이미 clone을 완료한 팀원은 다시 clone할 필요 없음):

~~~powershell
git fetch origin --prune
git switch dev  # 최초 1회: git switch -c dev --track origin/dev
git pull --ff-only origin dev
git switch -c feature/my-task
~~~

수정 후:

~~~powershell
git status
git add -p
git commit -m "feat: 기능 요약"
git push -u origin feature/my-task
~~~

담당 브랜치의 CI와 실제 검증 결과를 docs/VERIFICATION_LOG.md 양식으로 남긴다. 각 PC가 이미 `main`에 있으면 미커밋 파일을 보존한 상태에서 `dev`로 이동한다. **`dev` 자체 병합 시 동료 컨펌은 필요 없다.** `main` 직접 푸시·병합은 승인 없이 금지한다.

**담당자 자체 병합 예시 (PowerShell, PR 없이 가능):**

~~~powershell
# feature/my-task에서 자체 테스트와 안전·규정 확인을 완료한 뒤
git fetch origin --prune
git switch dev
git pull --ff-only origin dev
git merge --no-ff feature/my-task  # 충돌이 나면 해결 후에만 진행
# 변경 영향 테스트를 실행하고, 문제가 없으면
git push origin dev
~~~

- 다른 사람이 먼저 `dev`를 갱신해 푸시가 거절되면 **강제 푸시하지 말고** 최신 `dev`를 다시 받아 충돌·테스트를 재확인한다.
- GitHub PR을 사용해도 **head=본인 기능 브랜치 / base=`dev`**로 지정하고 본인이 병합한다. 별도 리뷰·컨펌 불필요.
- `dev` CI가 병합 후 실패하면 해당 기능 담당자가 원인을 수정하거나 자기 변경을 되돌린다. 검증되지 않은 위험 기능은 사용 가능한 상태로 두지 않는다.

**기능 담당자 자체 병합 흐름:** 기능 개발 → 자체 테스트·규정 검사 → 최신 `dev` 반영·충돌 해결 → 본인 `dev` 병합·푸시 → `dev` CI 확인·사후 복구. **타인 컨펌 대기 없음.** 안전·규정 검증은 생략할 수 없다.

**최종 릴리스:** 별도 팀 승인 → `dev` 검증/제출 SHA 결정 → `dev`를 head, `main`을 base로 하는 릴리스 PR → diff/CI/APK/공모전 규정 최종 확인 → 통합 담당자 병합 → `main` 릴리스 커밋·제출용 SHA 기록. **AI가 이 단계를 자동 수행해서는 안 된다.**

## 5. 병합 규칙 (기능→dev는 개인 자체 병합, dev→main은 승인 필수)

- 다른 기능·공유 인터페이스에 영향을 주는 변경은 기록·공유하되 다른 사람의 확인 회신을 기다리지 않는다. 담당자가 충돌·회귀 문제를 스스로 해결한다.
- **각 기능 담당자가 자기 브랜치를 최신 `dev`에 직접 병합한다.** 기능별 PR은 선택이며 사용 시 base=`dev`이다. `main`을 base로 선택한 기능 PR은 정정한다.
- **담당자 본인이** 병합 전 관련 테스트·Android 영향 빌드·출처 표시·안전 잠금·[SAFETY_RULES.md](SAFETY_RULES.md) G1~G5를 확인한다. 안 한 테스트나 에뮬레이터 시험을 PASS로 기록하지 않는다.
- `dev` 병합 직후 담당자가 영향을 받는 테스트와 CI를 확인하고 결과를 기록·복구한다. 최종 릴리스만 별도의 `dev → main` PR과 팀 승인 후 `main`에서 테스트한다.
- 실패 시 원인을 해결하거나 해당 통합을 되돌린다. `dev`·`main` 모두 강제 푸시로 이력을 덮지 않는다.
- 1차 제출은 **`main`의 제출 기준 커밋/태그를 고정**해 `dev`의 개발 중 변경과 구분한다. 공모전 공식 제출 SHA와 실제 APK·영상의 버전이 일치해야 한다.
- **기술적 제한:** 현재 GitHub 비공개 저장소에서 서버 측 branch protection/ruleset을 설정할 수 없는 플랜 제한이 확인됐다. 지금은 문서·AI 지침·CI가 사고를 줄이는 장치지만 **잘못된 푸시를 GitHub 서버가 강제로 차단하는 상태는 아니다**. 가능해지면 GitHub 보호 규칙에서 `main` PR 필수, 직접 푸시·force push 금지, 필수 CI를 설정한다.

## 6. 문서와 제품 규칙

- 최종 DOCX: 제품 요구사항(아직 구현되지 않은 계획을 포함).
- docs/IMPLEMENTATION_STATUS.md: 현재 구현 사실. 반드시 기준 SHA와 코드 경로 명시.
- docs/VERIFICATION_LOG.md: 실제 테스트 결과. 기기, SDK, 일시, 증거를 기록.
- docs/FACT_AUDIT.md: 기존 Markdown의 정정 및 미해결 목록.
- 차량 제어 API 금지, 미확인 SDK 시그니처 추측 금지, 신호 불명 시 안전 잠금 우선.
- 계정·연락처·키스토어·토큰·운전자의 민감한 정보는 Git에 넣지 않는다.
